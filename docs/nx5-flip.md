# NX5 阻塞翻页：29 FPS 上限的原因

当前 #233 固件的上限来自 **约 58 Hz 的实际显示时序，加上两个刷新周期的阻塞提交链路**。在保留当前双 framebuffer 完成等待的条件下，应用层优化不能稳定达到 30 FPS。本轮没有改变显示时序、驱动模块或正式渲染代码。

## 标称 60 Hz 为何实际只有 58 Hz

匹配设备 SHA256 的 `lcm.ko` 中，`_lcm_rgb_sync_info`（`.data + 0x13f0`）配置如下：

| 项目 | 水平 | 垂直 |
| --- | ---: | ---: |
| 有效区域 | 1024 | 600 |
| 前肩 | 160 | 12 |
| 同步脉宽 | 1 | 1 |
| 后肩 | 159 | 22 |
| 总计 | **1344** | **635** |

`lcm_func_probe()` 按总宽 × 总高 × 标称帧率计算所需像素时钟，即 **51,206,400 Hz**。VOU 的 `_check_vou_hdmi_reg()` 从离散时钟表中选择最近一档；相邻项为 49.5 MHz 和 56.25 MHz，因此选中 **49.5 MHz**，配置值为 `0x43a9`。

实机只读观测相互吻合：

- `HBLANK_INFO = 0x009f053f`：总宽 1344。
- `TF_BLANK_INFO = 0x0016027a`：总高 635。
- 时钟寄存器 `0x2800006c = 0x1a2043a9`：驱动所写的低 20 位为 `0x43a9`。
- VOU 中断实测 **57.9986 次/秒**；由配置计算为 **58.0006 Hz**。

因此 `/proc/umap/vo` 的 `DevFrt=60`、`/sys/module/lcm/parameters/fps=60` 是标称配置值，不是实际测量值。当前 LCM 参数文件均为只读。

```text
实际刷新率 = 49,500,000 / (1344 × 635) = 58.00056 Hz
双周期帧率 = 58.00056 / 2              = 29.00028 FPS
```

表项、模块哈希及实机读数见 [驱动数据](../evidence/nx5-flip/driver-tables.json)、[时钟读回](../evidence/nx5-flip/clock-readback.txt)。反汇编证据见 [关键函数](../evidence/nx5-flip/driver-excerpts.txt)。判断来自当前模块二进制及寄存器观测；手头没有匹配版本的驱动源码。

## 阻塞调用具体等待什么

`fyfb_fb_pan_display()` 先用 `down_trylock()` 消耗旧信号，调用 VOU 图形更新接口，再执行 `down()` 等待；`fyfb_notify()` 调用 `up()` 唤醒它。该函数没有固定睡眠，也没有根据 `activate` 标志切换出一个更快的提交分支。

VOU 将 surface 排入内部队列，刷新回调经 `HIL_VO_UFL_SurfaceDisplay()`、`HAL_VO_IRQ_GuiUpdate()` 应用图形更新。shadow 完成与缓冲区通知处理随后经 VOU 回调回到 fyfb。连续提交的观测时间轴为：

| 相对提交时刻 | 观测 |
| --- | --- |
| 0 ms | 提交新页，调用进入等待 |
| 约 17.2 ms | 配置地址变为新页，OSD `update_rdy` 置 1 |
| 约 34.48 ms | 更新位清零，阻塞调用返回，可按现有契约交换页角色 |

120 次稳定样本中，探针首次看到新地址及更新位的平均时间为 17.636 ms，至调用返回还有约 16.797 ms。探针有采样延迟，这些时间不能当作精确硬件边界；完成间隔及 58 Hz 的关系则由独立数据交叉确认。

驱动的自定义 `fyfb_fb_ioctl()` 只打印参数并返回 0。因此即使 `FBIO_WAITFORVSYNC` 返回成功，也不能把它当作有效等待或旧页退休依据。地址已变、更新位置位、增加固定睡眠也都不能替代当前完成等待。

## 相位扫描验证

测试暂停现有显示所有者，不加载 SDK、不写像素、不写寄存器，只交替 PAN 两张已有页；结束后恢复原页号并继续同一个 PID。测试线程与观察线程分别绑定 CPU0/CPU1。观察器会增加 CPU 负载，因此同时保留了上一轮无观察器的纯翻页基准作对照。

| 提交前准备时间 | 样本数 | 平均完成间隔 | 对应周期 |
| --- | ---: | ---: | ---: |
| 0 ms，去掉 8 次预热 | 120 | 34.48250 ms | 2 |
| 8 ms | 32 | 34.48223 ms | 2 |
| 15 ms | 32 | 34.48225 ms | 2 |
| 0–17 ms，每次增加 0.5 ms | 35 | 34.48245 ms | 2 |
| 17.5–31.5 ms，每次增加 0.5 ms | 29 | 51.72345 ms | 3 |

总计 256 次翻页均成功，两页交替，返回后的偏移、地址和更新位检查通过。无准备的完成速率为 **29.00022 FPS**。这排除了通过改变应用提交相位或减少 GET 查询稳定达到 30 FPS 的方案。

初版诊断的短 `nanosleep()` 在该内核上产生毫秒级量化，记录保留为 `phases.log`，不用于精确相位结论。最终 `precise.log` 对短延迟使用单调时钟计时，正式应用没有引入忙等。

## 达到 30 FPS 的可行修改位置

优先在 BSP 修正实际输出时序至 60 Hz，保留完整双周期提交。这样双页生命周期不变，理论周期从 34.482 ms 变为 33.333 ms。两条候选路线是：

1. 保持 1344×635 总时序，增加经过硬件验证的 **51.2064 MHz** 时钟项。当前离散表没有这一档；不能仅改表中的频率数字，还要提供正确的 PLL/分频配置。
2. 保持 49.5 MHz，按真实面板数据手册调整消隐，使 `Htotal × Vtotal = 825000`。例如 1320×625 在数学上恰好为 60 Hz，但其前后肩组合是否适合当前面板尚未确认，不能直接部署。

直接切到下一档 56.25 MHz，会把原时序推到约 **65.91 Hz**，不能当作 60 Hz 修复。单改标称 `fps` 或应用定时器同样不够。

另一方向是在 VOU 驱动中提前处理新 surface，并提供明确的旧页退休通知，把提交流水线缩短至一个刷新周期；这需要匹配源码和完成语义验证。当前用户态缺少这样的可靠接口，故本轮保留原阻塞契约与软件回退。

后续 [单周期调查](nx5-single-cycle.md) 对 128 次提交读取了匹配驱动的队列、待锁存和当前页状态，确认两个阶段各占约一次刷新；完成通知没有额外拖延一个周期。当前仍未实现安全单周期提交。

本轮没有增加新的像素或物理链路无撕裂证明。原先的 WBC 观测范围仍适用；时序或完成机制一旦改变，必须重新验证两页像素、持续帧率、旧页复用及真实输出。当前设备已恢复优化演示，运行状态见 [环境记录](../test-app/devices/nx5/current-target.json)。

## 复跑

```sh
sh test-app/tools/nx5/flip/build.sh
python3 test-app/tools/nx5/flip/analyze.py evidence/nx5-flip
# 当前应失败，说明不能达到 30 FPS，而不是将 29 四舍五入计为达标：
python3 test-app/tools/nx5/flip/analyze.py evidence/nx5-flip --min-fps 29.9
```

设备上的 `probe` 默认进行 10 秒只读观测。`--flips` 需要先确认并暂停当前显示所有者，再设置 `NX5_STOPPED_OWNER=<PID>`；仅在 `done failed=0 dropped=0 restored=1` 且程序成功退出后恢复所有者。工具不负责关闭或重置 SYS/VO。
