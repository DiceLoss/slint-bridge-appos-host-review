# NX1 渲染与内存分析（2026-10-20 开始的一轮测试）

基线为 `7f72336` 的 NX1 后端和现有 showcase。
本轮仅在隔离目录构建计时和优化原型，生产渲染源码未修改，原型代码未提交。
2026-10-21 决定维持现有效果，暂不落地优化；下文候选及实验开关不属于当前库功能。
设备、PAN 参考约定及其限制见 [NX1 接入报告](nx1-framebuffer.md)；
运行方式见 [设备说明](../test-app/devices/nx1/README.md)。

## 结论

主要瓶颈是 CPU 绘制，尤其是图片采样和混合，而不是 framebuffer 写页。
等尺寸不透明图片的整行复制原型，在相同功能与资源下使主要动态场景的
提交帧率提高约 37%–55%，没有增加图片缓存或画布。

进一步的应用级空间主要是混合透明行的连续区段处理、批量像素混合，
以及不透明背景的 RGB 存储。当前没有证据支持优先取消保留画布。
系统另有约 10.25 MiB 空闲 ION 预留区，但它不是普通堆可用内存，
需要独立验证缓存属性和生命周期，不能直接计作已经获得的内存收益。

## 方法与口径

- 同一 Cortex-A7 / Linux 3.4.39 设备，boot ID
  `0340c5fe-57ae-4c9e-9235-b58ccc9e3eb7`；未修改频率、内核或显示模式。
  当前固件不提供标准 cpufreq 频率节点，未用 BogoMIPS 推断运行频率。
- 与当前程序相同的 UI、图片、字体、分辨率、双页和预渲染调度。
  比较使用同一实验二进制，通过环境变量开启或关闭整行复制。
- 顺序为基线 → 候选 → 候选 → 基线。
  动态场景每次预热 4 秒、测量 20 秒，静态场景测量 8 秒；
  完整时间窗口内累计统计 9971 次成功返回的 PAN。
- 纵向/横向列表由设备本地原生 MCP 客户端每次移动 20/40 px，
  请求间隔至少 20 ms，每 3 秒换向，保持在列表中段。
  SVG 尺寸和透明度以至少 40 ms 间隔连续设置。
  这是明确的交互负载，不是无输入限制的离屏吞吐。
- 记录绘制、写页、PAN 的墙钟和线程 CPU 时间、实际写入像素数；
  自定义纹理处理时间是绘制时间的子集，不能重复相加。
  PAN 等待与下一帧预渲染重叠，也不能把三段墙钟直接相加当作帧周期。
- 每秒读取进程 stat/status/smaps 与系统内存；同时记录 mallinfo 的活跃堆、
  空闲块和大块 mmap 分配。固定窗口内没有新增 major fault。
- `perf_event_open` 的硬件和软件事件均返回 ENOSYS；
  本轮没有函数级采样火焰图或硬件 cache-miss 数据。

计时器和观察器有成本：同一 Overview 控制负载中，计时开启为 19.05 FPS、
关闭为 19.62 FPS，差约 2.9%；观察器自身最高约占 1.2% CPU。
所有 A/B 均使用相同计时和采样条件。下面是诊断版的稳定窗口测量，
不把小数位当作实际业务的性能承诺。

最初一次控制脚本从主机读取尚未刷回的 NFS 日志，误判 MCP 未就绪。
应用和观察器均正常退出；该轮只保留为默认 Overview 的校准记录，
不计入完整 A/B。之后改为在设备侧读取活动日志，四轮均正常完成并退出。

## 当前渲染成本

两轮基线合并结果，单位为毫秒/帧：

| 场景 | 提交 FPS | Slint 绘制墙钟 | 转换与写页墙钟 | PAN 墙钟 |
| --- | ---: | ---: | ---: | ---: |
| Overview | 19.44 | 48.11 | 2.79 | 8.65 |
| Motion | 21.61 | 43.35 | 2.39 | 8.54 |
| 富列表纵向 | 8.56 | 107.23 | 4.94 | 9.22 |
| 富列表横向 | 8.38 | 110.10 | 4.68 | 8.64 |
| PNG/SVG 连续缩放 | 13.31 | 69.17 | 3.51 | 9.02 |
| 图片背景上的透明度变化 | 23.21 | 23.25 | 1.64 | 8.59 |
| 隐藏图片背景后的透明度变化 | 23.35 | 13.65 | 5.99 | 8.67 |

前五个场景的进程 CPU 约为单核的 97%–98%。
Overview 的自定义纹理处理占绘制 CPU 时间约 39%；
富列表纵横向约为 86% / 83%。
静态 Controls、静态缩放页和返回 Controls 时，提交 FPS 为 0，
CPU 约 0.7%–0.8%，没有持续全屏刷新。

当前写页已经按脏区工作：上述动态场景通常约写 210–1062 KiB/帧，
而整页为 2400 KiB。透明输出的反预乘路径较贵，
约 6 ms 写入 210 KiB；这与普通不透明页面的写页成本不同。

showcase 的动画数据由 [33 ms 定时器](../test-app/src/showcase.rs) 更新，
约为 30 Hz。Motion 优化后接近这一节拍，不能因此认定驱动只能输出 30 FPS。
之前简单 display 的约 59 FPS 属于另一种负载。
所有“提交 FPS”都按当前参考 PAN 返回口径统计，不证明旧页硬件退休或无撕裂。

## 已验证的整行复制候选

原型仅处理无旋转、无缩放、无 colorize/tiling、整体 alpha=255 的等尺寸图片：
RGB 行直接展开到 RGBA；RGBA/预乘 RGBA 行只有所有 alpha 都为 255 时才复制。
其他情况继续原处理，包括半透明像素、缩放、旋转和裁剪回退。

| 场景 | 基线 FPS | 候选 FPS | 变化 |
| --- | ---: | ---: | ---: |
| Overview | 19.44 | 27.68 | +42.4% |
| Motion | 21.61 | 29.54 | +36.7% |
| 富列表纵向 | 8.56 | 13.27 | +55.0% |
| 富列表横向 | 8.38 | 12.57 | +49.9% |
| PNG/SVG 连续缩放 | 13.31 | 19.72 | +48.1% |
| 图片背景上的透明度变化 | 23.21 | 23.33 | 请求节拍限制，帧率接近不变 |
| 隐藏图片背景后的透明度变化 | 23.35 | 23.31 | 接近不变 |

Overview 的纹理 CPU 时间由约 18.4 降到 2.3 ms/帧，
而写页仍约 2.8 ms，PAN 仍约 8–9 ms。
图片背景上的透明度场景 CPU 由约 61% 降至 43%，
帧率受请求节拍限制；隐藏图片背景后的场景没有同类收益。
这些结果与候选只加速不透明图片这一机制一致。

功能和画质检查：

- 原有 NX1 workspace 主机回归通过，并补充 1152 帧完全不透明/混合行对照；
  与原有 576 帧纹理序列一起覆盖三种像素格式、四种旋转、
  分数位置、裁剪、透明度及保留缓冲重绘。
- 候选完成九页原生 MCP 检查、18 张设备卡片、
  纵横两轴各 100 个富列表 ID、边界、选择、弹窗、键盘及透明开口。
- 24 张物理页采样中，23 张静态图与当前版本逐像素一致，最大通道差为 0。
  Motion 两次暂停的 UI ticks 分别为 536 和 18，动画相位不同，
  未把该图计作同帧像素一致性通过。
- PNG/SVG 四档缩放的实际色块与裁剪检查通过。
  未使用设备上的 MCP 软件重绘代替这些物理页比较。

原型没有新增持久像素缓存。基线/候选的采样 RSS 最大值均为 15052 KiB；
进程高水位最大值分别为 16132 / 16188 KiB，约 15.75 / 15.81 MiB。
不能仅凭某次返回页面的 RSS 波动认定它增加了固定缓存。

## 内存账

实验前原程序静态 Controls 的一次快照为 RSS=12408 KiB、
PSS=12024 KiB、匿名页=6744 KiB，约 12.12 / 11.74 / 6.59 MiB。
本轮固定工作负载的峰值低于上一轮完整交互报告中的约 17.6 MiB；
页面历史和诊断活动不同，这不是已经优化了内存的证据。

| 项目 | 大小或观测 |
| --- | --- |
| 物理 RAM | 内核启动记录为 64 MiB |
| Linux MemTotal | 43532 KiB，约 42.51 MiB |
| ION 预留池 | 15 MiB，`0x43100000..0x43ffffff` |
| 当前 ION 忙区 | `/proc/sunxi_ion` 报告 `0x4b0000`，4.6875 MiB，等于双 framebuffer |
| 当前 ION 空闲 | `/proc/sunxi_ion` 报告 `0xa40000`，10.25 MiB；不是普通堆可用内存 |
| 保留 RGBA 画布 | 1024×600×4 = 2.34375 MiB |
| 当前 RGBA 背景像素 | 同为 2.34375 MiB |
| 字体文件数据 | DejaVuSans.ttf 为 759720 B，约 0.725 MiB |
| 初始 Controls 活跃堆 | mallinfo 的 used+mmap 约 6245 KiB |
| 富列表采样 RSS / PSS 最大值 | 15052 / 14656 KiB，约 14.70 / 14.31 MiB |

framebuffer 的进程映射 Size 为 4800 KiB，但 smaps Rss/Pss 为 0。
应把它作为驱动持有的物理资源单列，不能当成免费内存，
也不能重复加到进程匿名堆中。
ION 输出按 64 KiB 单位统计，本轮没有强行把 busy/free 数值凑成完整 DDR 总账。

两轮基线返回 Controls 后 RSS 为 14104–14860 KiB。
5 次列表进入/切换方向/退出后，没有观察到持续线性增长；
活跃堆约 6.6 MiB，另有约 0.8–1.3 MiB 空闲块留在分配器中。
实验性地在空闲期调用一次 malloc_trim 后，四轮释放 368–912 KiB RSS，
最终收敛到 13728–13736 KiB，活跃堆基本不变。
这支持其中一部分是分配器保留，而不是活跃对象或泄漏。
剩余增长还包含访问更多页面后的文件代码页与活跃渲染缓存；
本轮没有逐个分配归因，也不替代长时间压力测试。

同一含 MCP 和调试元数据的二进制，只关闭监听服务、不查询 UI 时，
Overview RSS 从 11508 降到 11364 KiB，少约 144 KiB，线程从 3 变 2。
这只量化被动服务开销，**不是**编译期移除 MCP/元数据的总收益；
不把删除现有诊断能力作为本轮保持功能的优化。

## 后续优先级

1. **优先收敛等尺寸图片快速路径。**
   已有上述实机收益和像素验证；正式实现需要移除实验开关/计时，
   明确只在已验证条件下命中，并保留完整回退。

2. **扩展到混合透明行的连续区段或小块处理。**
   富列表 PNG 中，不透明像素约占纵向素材的 78.55%、横向素材的 86.95%，
   但每行边缘的透明像素使整行复制条件经常不成立。
   候选之后，列表纹理处理仍约 49 ms/帧。
   对透明区、完全不透明区和真正需要混合的区段分别处理，
   可以减少逐像素坐标计算与中间采样；需要保持原来的逐步 `/255` 取整。
   这是源码与像素分布支持的下一候选，尚未给出实测收益。

3. **检查连续同色填充/混合和透明写页的批量实现。**
   Overview 优化后仍约 31.6 ms 绘制，且大部分已不在纹理回调中；
   透明页面写页约 6 ms。可借鉴现有 NX5 的 CPU 批量混合算法，
   但不引入其 SDK、DMA 或板级 alpha 编码。
   本轮没有函数级采样，不能把剩余时间全部归因于圆角或文字。

4. **不透明背景改用 RGB 存储。**
   原始像素存储差额为 1024×600×1 = 614400 B，约 0.586 MiB。
   必须确认背景完全不透明，并验证 NX1 解码/渲染链路是否保持三通道。
   该数字是明确的像素存储潜力，本轮未另做 RGB 的 NX1 A/B。

5. **有条件地处理空闲堆，而不是每帧回收。**
   本轮单次回收约 0.36–0.89 MiB，收益有限且受分配历史影响；
   若采用，需要再测重入页面的缺页与首帧代价。
   字体文件映射也可另行评估，但本字体只有约 0.725 MiB，
   文件映射主要改变匿名/文件页性质，不保证 RSS 同量下降。
   没有启用先前暂存的共享 Slint 字体修改。

6. **把空闲 ION 作为单独的板级内存课题。**
   可调查把 CPU 保留画布或合适的只读像素放入可缓存 ION 内存，
   利用现有预留池缓解 Linux 普通内存压力。
   必须先验证缓存属性、CPU 读改写速度、分配/释放及异常生命周期。
   这属于内存池之间的转移，不是减少同等数量的实际 DDR 像素。
   缩减 ION 预留则涉及固件和其他客户端，本轮均未实施。

不优先直接写 framebuffer：当前不透明场景写页只占几毫秒，
取消保留画布会改变预渲染和 CPU 读改写条件。
此前 F1 的直写结果也不能替代 NX1 的独立验证。
