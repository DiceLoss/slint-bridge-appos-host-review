# NX5 PNG / SVG 单独运行时缩放开销

2026-10-14，在同一 NX5 #233、Slint `22804ff` 和 `abb2e33` 展示应用基础上，分别测量 PNG、SVG、空图及双图。此次只测量，不修改正式运行时或部署新功能。此前双图的 25.87 FPS / 88.35% CPU 仍保留在[原报告](nx5-runtime-scaling.md)，不将它替换为本次诊断结果。

## 结果

| 场景 | 完成提交 FPS | CPU（单核） | 动态 RSS 均值 / 范围（MiB） | 缩放前 RSS（MiB） | 进程 VmHWM（MiB） |
| --- | ---: | ---: | --- | ---: | ---: |
| 空图对照 | 28.96 | 57.70% | 13.32 / 13.32–13.32 | 13.26 | 13.72 |
| 仅 PNG | 28.99 | 65.23% | 13.49 / 13.49–13.49 | 13.43 | 13.85 |
| 仅 SVG | 28.06 | 84.38% | 14.83 / 14.78–15.41 | 14.45 | 15.41 |
| PNG + SVG | 25.99 | 88.14% | 15.05 / 15.00–15.61 | 14.60 | 15.62 |

PNG 单独缩放达到 **28.99 FPS**，接近现有约 29 FPS 的完成提交上限；SVG 为 **28.06 FPS**。单独 SVG 比单独 PNG 多 **19.15 个 CPU 百分点**，动态 RSS 均值多 **1.34 MiB**。双图为 25.99 FPS / 88.14% CPU，与此前双图结果接近。

空图对照仍为 57.70% CPU，说明基础界面、输入处理、重绘、调度与写页已经有显著开销；这不是空闲 CPU。静态 5 秒窗口四组均约 15%，仅用于获取本进程缩放前的内存基线。

所有组均为 3 个线程，MMZ 为 12100 KiB / 5 块。RSS 是整个进程的驻留内存，包含代码、应用、解码及分配器保留空间，不是单张图片大小；MMZ 单独列出，不与 RSS 简单相加。四组资源窗口均无 major page fault，原始样本同时保留系统 MemAvailable。

## 主要开销的判断

格式相关的额外负担主要在 **SVG 路径**。源码中 PNG 的 `ImageInner::EmbeddedImage` 返回已解码缓冲；SVG 的 `ImageInner::Svg` 调用 `ParsedSVG::render`，按当前目标尺寸新建 RGBA 缓冲并调用 `resvg::render`。SVG 的 XML 在加载时解析，持续缩放的额外工作是栅格化与缓冲处理，并非每帧重新解析 XML。

当前 NX5 TDE 纹理入口拒绝源与目标尺寸不相等的作业，所以 PNG 的多数非 100% 比例由软件缩放。SVG 先生成目标尺寸位图，随后是否走 TDE 还取决于尺寸对齐、面积等条件；不能将 SVG 全部算作硬件缩放。这些代码路径与本轮资源差异一致。

本轮没有对 resvg、软件采样、TDE 上传、界面合成和写页分段计时，因此不能把两个 CPU 百分比的差值全部归给某个函数。空图和有图的损伤区域也可能不同。此处结论限于这份 256×160、简单图形素材在 50%–200% 的缩放；复杂 SVG、其他分辨率或纯图片页面需要另测。

## 公平性与统计口径

临时诊断补丁只选择加载 `none/png/svg/both`，单 PNG 和单 SVG 都放在同一个左侧预览窗，右侧留空；双图维持原左右布局。未选中的源不加载。滑块、背景、固定卡片、裁剪窗和尺寸范围相同。原始资源没有构建期缩放；四种模式均经主机原生 MCP 截图像素检查，确认左、右预览存在或为空。诊断补丁和二进制摘要随原始证据保存，构建完成后正式源码逐字节恢复。

每组使用新进程。CPU/RSS 窗口关闭 trace、截图与事件录制，先静态采样约 5 秒、拖动预热至少 8 秒，再测量至少 45 秒并完成最后一个手势；约每秒从进程外读取 `/proc/PID/stat`、`status` 和设备 uptime。CPU 按已核验的 100 Hz jiffies 计算，占满一个核心为 100%。

FPS 另开进程，使用已有低频 trace 的成功完成提交批次，每批 150 帧，丢弃跨过测量起点的第一批。不使用 UI timer 帧号，不混入该 trace 窗口的 CPU/RSS。每种模式各有一个资源窗口和一个帧率窗口，属于有限样本而非长期稳定性认证。

原生 MCP 以相同的小步拖动路径交替前往两端，但绘制会对输入形成背压，因此没有声称各组输入频率相同。CPU 差值不是可相加的阶段占比。实际手势数和有效批次如下：

| 场景 | CPU 窗口秒 / 手势 | FPS 窗口秒 / 手势 | 有效提交数 | 批次 FPS 范围 |
| --- | --- | --- | ---: | --- |
| 空图对照 | 45.18 / 48 | 45.12 / 48 | 1050 | 28.81–29.00 |
| 仅 PNG | 45.87 / 36 | 46.57 / 36 | 1200 | 28.90–29.00 |
| 仅 SVG | 45.52 / 27 | 45.55 / 27 | 1200 | 27.80–28.43 |
| PNG + SVG | 45.71 / 24 | 45.80 / 24 | 1050 | 25.44–26.61 |

## 验证、恢复与证据

诊断构建通过 feature 矩阵、格式、严格 Clippy、ARM release 及四种主机模式像素检查。首次主机预览曾被 feature 矩阵重建覆盖为不含 preview 的文件，未启动 UI；独立保存重建副本后四组通过。首次上传在创建 `/run` 子目录时权限不足，没有上传文件；root 创建本轮专属目录后，部署脚本的内存及摘要检查通过。原始失败记录保留。

诊断文件放在 `/run`，原常驻及三个恢复二进制都保留。实机性能阶段不截图，避免在额外二进制占用 tmpfs 内存时突破截图余量要求。旧常驻 SIGTERM 的内核回收单独记录，不当作有限进程正常退出结果。

八个有限进程均退出码 0、VO 关闭、MMZ 回到 4900 KiB / 2 块；后续 113 行新增内核日志没有 OOM 或 MMZ 强制回收。71 个本轮文件（含诊断二进制）经摘要核验归档清理，正式程序和全部三个恢复副本保留。原版常驻恢复为 PID **7333**，无定时器、trace 或 `NX5_SCALING_CASE`，左右双图为 100%。清理后 `/tmp` 使用 41692 KiB，`/run` 使用 804 KiB。

本地原始档案为 `evidence/nx5-scaling-formats/2026-10-14/`，被 Git 忽略，需另行取得。`manifest.json` / `diagnostic.patch` 保存来源，`host-*/` 保存隔离检查，`*-r1/` 保存关闭 trace 的资源样本，`*-f1/` 保存完成提交日志，`results.json` 保存汇总。软件路径依据本地同源 Slint 的 `internal/core/graphics/image.rs`、`image/svg.rs`、`internal/renderers/software/lib.rs`，以及本库 [TDE 纹理准入](../src/backends/nx5/tde/mod.rs)。

用户在 `none` 窗口反馈 SVG 未显示；该窗口本来就禁用两图，单 SVG 窗口也刻意使用左侧预览。收尾恢复原版后，额外只读采集两张物理 framebuffer 页的 y=300/390 行，核对左右图片各四色、合计 16 个采样点。BGRA 及 NX5 alpha=128 与恢复后的原生截图一致，右侧 SVG 确实写入两张显示页。这是选点验证，不是整帧或 LCD 扫描认证；未新增 WBC、evdev 或手指触摸测试。恢复后的实际程序和 PID 见 [设备说明](../test-app/devices/nx5/README.md)，使用前重新核对显示所有者。
