## 性能方法

最终结果均取自上述新启动、同一个 release 文件。CPU/RSS 与 FPS 分别使用新进程，前者关闭 trace、截图和事件录制，每秒从进程外采样 `/proc/PID/stat`、`status` 与设备 uptime，CPU 以占满单核为 100%。后者使用已有低频 trace，以成功完成 PAN 的完整 150 帧批次统计；丢弃跨过阶段开始的首批，不把 UI timer 当作 FPS。

每个方向先在长列表内部定位并预热至少 8 秒。资源窗口至少 45 秒，帧率窗口至少 90 秒，完成最后一个手势后结束采样。每次拖动核对真实内容位移大于可视长度的 40%，且结束位置仍在列表内部；接近边界前换向，避免把端点停留算作持续运动。原生 MCP 的可见卡片查询、手势插值与等待均包含在负载中，不能等同于固定频率的 evdev 或手指输入。

## TDE 参与程度

既有日志按绘制帧记录成功复制、混合、软件纹理回调和源纹理缓存命中。以下分别取纵向 1050 个、横向 900 个绘制帧的完整计数边界差分，与上表的完成提交窗口区分：

| 方向 | TDE 复制 / 绘制帧 | TDE 混合 / 绘制帧 | 软件纹理回调 / 绘制帧 | 成功硬件纹理操作的缓存命中率 | 错误 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 纵向 | 0.98 | 1.25 | 180.72 | 37.33% | 0 |
| 横向 | 0.99 | 1.62 | 223.04 | 37.82% | 0 |

TDE 已实际参与大块纹理复制和混合。小 SVG 的栅格化、文字及未满足硬件条件的纹理仍由 CPU 处理；一次大图复制和一次字形绘制的像素量不同，所以这些调用数量不能换算成像素覆盖率或硬件忙碌率。成功硬件纹理操作中约 62%–63% 未命中源缓存，会走数据准备/上传路径；本轮未单独计时其 CPU 开销。

本板没有 `/proc/umap/tde`，相关 `/proc/umap/vppu` 提供近期 VDMA/VPPU 作业、`TimeCost` 和成功/失败计数，但没有可直接使用的累计 busy% 指标，且本轮未验证 `TimeCost` 的单位和排队语义。因此没有给出所谓“TDE 硬件使用率百分比”；37%–38% 仅指上述纹理缓存命中率。驱动快照保存为 `resident-vppu.txt`。

### 为什么可见两三张卡片，TDE 混合均值仍只有一点几

原生层还有一个关键限制：[native.c](../src/backends/nx5/tde/native.c) 要求混合矩形的 `sx/sy/dx/dy/width/height` 全为偶数；任一矩形不满足，就返回 `Unsupported`，整个纹理调用由软件重绘，且不计入 `errors`。这比 Rust 层的原图尺寸对齐检查更严格。

本轮归档的实际元素状态已经出现此条件：纵向采样结束时完整卡片的 y=260.9165、380.9165，取整后为 261、381；横向为 x=343.2559、599.2559，取整后为 343、599。纵向步距 120、横向 256 都是偶数，因此同一帧多张卡片会共享坐标奇偶性，可能一起回退。裁剪后不足 32768 像素及奇数裁剪边界还会进一步减少硬件混合。当前计数只记录成功执行的硬件混合，不是可见卡片数；尚未逐帧统计各回退原因的比例，不将“约一半”写成实测占比。

四张 PNG 的 alpha 范围均为 0–255。原生层按整张源图判断透明性，所以这里不能用“透明卡片改记为复制”解释缺失的混合次数。

使用生产 `native.c` 和主机 SDK 替身复现：800×112 透明图在 `(198,260)` 成功混合，改为 `(198,261)` 就在提交 SDK 作业前回退；244×328 图在 `(342,186)` 成功，改为 `(343,186)` 回退。奇数源 Y、奇数裁剪宽度也回退。奇数案例仍发生了一次源缓存刷新，因为当前奇偶检查位于源数据准备/刷新之后，这会产生额外 CPU 工作；其耗时未单独量化。原生故障注入与边界检查通过，补充诊断源码和结果位于本地 `blend-admission/`。本次仅核查原因，未改变准入或绘制行为，也未中断设备常驻。
