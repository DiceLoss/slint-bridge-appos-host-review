# 审查修复与 NX5 会话重试验证

2026-10-12 验证提交 `bccf6b9`，修复基于 `825b26f` 审查确认的三个问题：SDK VO 引用不配对、事件循环再次运行时先提交旧预渲染画面，以及文件锁竞争返回错误类别与接口说明不一致。源码及部署摘要见 [部署清单](../evidence/review-fixes/2026-10-12/deployment-manifest.json)，结果见 [验证汇总](../evidence/review-fixes/2026-10-12/results.json)。原始 `evidence/` 不随 Git 分发，重放需要另行取得这些档案。

## 修复与主机回归

- NX5 首次加载 SDK 后接管构造函数已有的 VO 引用；VO 尚未启用时才显式调用一次 `VO_Enable()`。后续 framebuffer、输入初始化失败或 UI 线程退出时配对释放。SDK 库映像保持驻留，重试复用 SYS/VB/MMZ 描述符缓存；正常会话仍关闭 VO 并释放独占锁。
- 事件循环退出时等待已提交帧完成，丢弃未提交预渲染帧；再次运行先绘制组件当前状态。丢弃帧的脏区继续参与后续两张物理页的修复，避免局部变化丢失。不会通过重新运行恢复失败的提交或未知 DMA 状态。
- 两处独占锁共用错误分类：竞争返回 `DisplayNotAdmitted`，其他调用错误保留 `Io`。
- 正确释放 VO 后会真正关闭 SYS，因此未知 TDE/DMA 状态还必须保留板级 SDK 会话和独占锁；这与原生层保留 MMZ 的策略配套，防止提前关闭仍可能工作的硬件。

针对性测试先复现失败再验证修复，覆盖 SDK 自动/非自动启用、驻留库重试、初始化错误清理、描述符缓存、正常退出和布局错误后的首帧、两页局部脏区修复及未知 DMA 会话保留。主机未加载真实 SDK。

## 同进程初始化失败与重试

操作前重新核对 USB1 root 会话、ADB `192.168.1.151:5555`、#233 内核及启动 ID `938c34d4-456a-4b1a-b532-678c0f92efd0`。原 PID 3698 经 MCP 暂停，提交线程空闲后以 SIGTERM 结束；该旧进程的内核 MMZ 回收单独保存，不计为新版本的正常清理结果。

专用 [init-retry.rs](../test-app/src/bin/init-retry.rs) 在同一进程内调用公开 `init()`：两次指定不存在的 framebuffer、两次指定不存在的输入设备，再成功启动并结束一个 UI 线程。每个检查点均在进程仍存活时读取 VO、MMZ 和自身设备描述符，避免进程退出回收掩盖泄漏。

最初仅修正 VO 配对时，实机发现描述符数量随卸载重载从 3 增加到 5、8、11。缓存的 `/dev/sys`、`/dev/vb`、`/dev/mmz_userdev` 在库卸载后遗失，因此补充 `RTLD_NODELETE` 和相应主机回归。最终结果如下：

| 检查点 | VO | TDE 分配 | 设备描述符数（含串口） |
| --- | --- | ---: | ---: |
| framebuffer 失败 1 / 2 | 均关闭 | 0 / 0 | 3 / 3 |
| 输入失败 1 / 2 | 均关闭 | 0 / 0 | 4 / 4 |
| 成功运行后的 UI 线程退出 | 关闭 | 0 | 4 |

程序返回 0，库构造函数只执行一次，重复会话的描述符不再增长。三个 SDK 缓存描述符仍随库映像驻留，不表示 VO 或 TDE 分配仍活动。内核日志没有该回归期间的新 MMZ 强制回收；输入初始化失败的快速清理期间可见驱动 `LAYER_DISABLED` 记录，随后成功会话和下方显示用例正常完成。

最终原始记录在 [device-restored/](../evidence/review-fixes/2026-10-12/device-restored/)，修复缓存前的记录在 [device-first/](../evidence/review-fixes/2026-10-12/device-first/)。

## 正常显示与资源清理

显示程序使用原自定义设备链接与 SDK/WBC 目录，未改动外部 Slint、SDK、驱动或固件。通过进程内观察器采集 WBC，没有并行启动另一个加载 SDK 的采集进程。

| 用例 | 结果 | 退出清理 |

现有 `check-run.py` 与 `check-exit.py` 验证正对照和纹理；负对照独立断言混色结果。三组均实际分配三个 TDE 块，退出后无新进程的内核强制 MMZ 回收，不能仅根据应用退出码判断负对照。

## 恢复状态与限制

首次恢复 PID 3949 后，MCP 暂停/恢复成功，但截图时设备发生 OOM，内核杀死显示进程并强制回收其 MMZ。此时 `/run` 占用约 43 MiB、`/tmp` 约 20 MiB，其中包括本轮约 5.7 MB 的临时 `init-retry` 二进制。异常保存在 `device-restored/mcp-oom.dmesg`，不混入前述正常退出结果。

已移除设备上的临时诊断二进制（主机仍保留可部署副本），重新启动 PID **3972**。最终用低内存的原生 MCP 属性查询确认 1024×600 窗口：暂停时 Frame 2058 保持稳定，恢复后从 2059 增至 2077，状态为 RUNNING。未再次截图，因此没有本轮最终截图通过的结论。

常驻路径为 `/tmp/slint-bridge-review-fixes/display`，SHA256 为 `8aba5bfd344fc60f32f90ace2467206abc326956e20efdc5bcd1878d5b2fd107`。最终快照为 RSS 11108 KiB、3 个线程、可用内存约 8640 KiB、MMZ 12100 KiB / 5 块；持续 trace、WBC 和故障注入关闭。旧 `c03c3bb` 程序及其启动脚本保留作为恢复入口，使用前仍须重新核对所有者。`/tmp` 与 `/run` 重启后不保留。

本轮没有重新执行三项独立 ignored 硬件测试、完整启动矩阵、输入 EIO 或用户实体触摸；这些仍以各自历史报告为准。未知 DMA 的隔离仅在主机故障注入中验证，没有在真实设备上注入不确定的硬件作业。WBC 样本也不等于全部物理帧的无撕裂认证。
