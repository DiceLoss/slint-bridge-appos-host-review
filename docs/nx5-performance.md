# NX5 性能测量与优化记录

本篇按实验阶段合并性能结论。除另行注明，设备为 NX5 / Linux #233、1024×600；CPU 以单核 100% 为口径，FPS 计成功完成提交。不同场景、版本和采样流程之间不能直接相减或累计收益；阶段计时与正式 FPS/资源窗口分开解释。

现行算法和默认策略只维护在 [平台说明](software-platform.md)，构建及工具入口见 [使用指南](getting-started.md) 和 [NX5 工具说明](../test-app/tools/nx5/README.md)。以下 `evidence/` 需另行取得，整理文档未产生新实测。

<a id="nx5-tde"></a>

## 初次 TDE 接入

512×384 缓存命中纹理，预热 5 帧、测量 60 帧；包含 TDE 提交、同步和当时的 MMZ/CPU 回拷，不含翻页。纹理、文字、移动图形混合的整屏软件/TDE 示例都约 19.2–19.5 FPS，因此纹理倍率不能当作整机倍率。后续共享画布另测。

| 操作 | 软件平均 | TDE 平均 | 加速比 |
| --- | ---: | ---: | ---: |
| 不透明纹理 | 16.606 ms | 6.550 ms | 2.54× |
| 普通 RGBA 透明纹理 | 35.252 ms | 13.192 ms | 2.67× |
| 预乘 RGBA 透明纹理 | 22.865 ms | 13.087 ms | 1.75× |

证据：`evidence/nx5-tde/`。

<a id="nx5-fps"></a>

## 早期 CPU 与写页优化

同一 1024×600 纹理场景由约 19.5 FPS 到 29.0 FPS。90 秒有 17 个完整 150 帧窗口，启动 28.43，其后 16 个为 29.00，TDE 错误 0。下表是该阶段串行流程计时，不能套用于后来的并行流水线。

| 阶段 | 优化前平均 | 优化后平均 |
| --- | ---: | ---: |
| Slint/TDE 绘制 | 15.58 ms | 11.95 ms |
| 转换并写入后台页 | 4.91 ms | 1.96 ms |
| 阻塞翻页 | 30.48 ms | 20.20 ms |
| 整帧间隔 | 51.34 ms | 34.48 ms |

证据：`evidence/nx5-fps/`。

<a id="nx5-parallel"></a>

## 绘制与提交并行

首次并行化保留两张物理页、一笔在途提交和一帧预渲染，只把完成等待移到后台。板级优化构建未获得额外 FPS；较慢通用构建收益明显。

| 构建方式 | 改动前串行 | 并行 |
| --- | ---: | ---: |
| Cortex-A7/NEON 优化构建 | 约 29.00 FPS | 约 29.00 FPS |
| 未启用板级 CPU 优化的 ARM 构建，仍使用 NX5-TDE 后端 | 21.17 FPS | 25.51 FPS |

证据：`evidence/nx5-parallel/`。

<a id="nx5-scheduling"></a>

## 等待精度优化

同一未启用板级 CPU 优化的 TDE 构建由约 25.51 到 29.00 FPS。内核定时节拍约 10 ms；阻塞到最后一个节拍前、再检查期限改善等待精度，同时增加 CPU。测量时仍有后续已移除的 33334 微秒帧间隔钳制。

| 等待方式 | 请求 33.334 ms 时的实际等待中位数 |
| --- | ---: |
| `poll` | 39.925 ms |
| `ppoll` | 39.916 ms |
| `nanosleep` | 39.927 ms |
| `timerfd` | 39.925 ms |
| 阻塞等待后检查最后期限 | 约 33.336 ms |

| 口径 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 一个 CPU 核心为 100% | 44.69% | 50.56% |
| 换算为双核总算力占比 | 22.34% | 25.28% |

证据：`evidence/nx5-scheduling/`。

## 与 X9 的 MCP 内存增长对照

2026-10-16，在 NX5 #233 上对照 [X9 的动态元素查询归因实验](x9-performance.md#x9-growth-attribution)。**增长机制一致：静态查询与预热后的单纯切页基本不累积；动态元素树查询保留已析构组件的弱引用；停止枚举后增长停止；句柄达到 10,000 后，同一负载下进入平台。** 两台设备的 RSS 变化幅度及空闲页回收行为不同，不能直接比较总 RSS 来推断对象是否释放。

### 对象、版本和方法

执行前重新核对 USB1 root、ADB `192.168.1.151:5555`、Linux `4.9.138 #233`、boot ID `4aa4f5d2-8de2-42cb-9c2b-44c3e74d6e2b` 和显示所有者。实际常驻应用是 music-player PID 8008，而非旧快照中的 background-holes。用户明确选择临时切换 showcase 做同场景对照，完成后恢复音乐应用；原音乐进程的 31 个静置样本 RSS 均为 8,292 KiB，这组数据不并入 showcase 对照。

使用板上已有、摘要与历史构建档案一致的 showcase：SHA256 `e2a0f1245c3a471329091f215b68311f16362db954837901e63b4fcc53449f39`，bridge `2fddc04`、Slint `9a1a3b14`，`nx5-tde,slint/mcp`，1024×600、0°。X9 为较新的卡片缓存版、Slint `c878901`、1280×800 逻辑窗口；核对这两个 Slint 提交的 `introspection/mod.rs`、`search_api.rs`、`vrc.rs`，三份源码逐字节相同。没有重编译或替换应用，也没有修改实现。

临时 showcase PID **15369** 于主机 UTC **12:10:24 左右**启动，`--seconds=600`，于 **12:20:25** 正常退出。native MCP 沿用 X9 的 Rich list 纵向首页 → Controls 循环、每页 250 ms、阶段结束等待 2 秒的脚本。先预热 Controls 查询，再单独预热一次 Rich/Controls；首次图片/字体及缓存加载不混入后续循环增量。依次执行静态查询、40 轮仅切页、40 轮切页加树查询、40 轮停止枚举、180 轮枚举达到上限、上限后再枚举 80 轮。后两组每次重新查找导航句柄，避免使用已被 FIFO 淘汰的旧句柄。

NX5 libc 同为 glibc 2.21，但内部 arena 布局与 X9 不同，读取器按本机 SDK DWARF 重新校准：设备与 SDK 的全部 PT_LOAD 字节仅有 strip 改写的 ELF 节表头字段不同。独立 fixture 的 arena、free、inuse、mmap、fastbin、top 六项与进程自报 `mallinfo()` 完全相同；MCP TLS 符号与活句柄数量也经过核验。只读快照短暂停止三个线程，耗时 **10～230 ms**，随后全部分离；不向进程写内存、不注入函数、不调用 trim。实验期间没有截图或事件录制；音乐暂停前的恢复用截图单独保存，不计入 showcase 测试。

### 相同动作的在用量变化

下表是 **malloc arena 在用分配块字节**，包含块开销，不是 RSS，也不等于业务对象有效载荷。预热后 NX5 的独立 mmap 分配量一直为 **3,584,000 B**。

| 对照阶段 | NX5 在用增量 | X9 在用增量 | NX5 的 MCP 可归属增量 |
| --- | ---: | ---: | ---: |
| 3,000 次静态属性 + 300 次相同树查询 | **0 B** | **0 B** | 0 B |
| 40 轮仅切页 | **+808 B** | −64 B | 0 B |
| 40 轮切页，每轮查询 Rich 元素树 | **+423,840 B（413.91 KiB）** | +471,168 B（460.13 KiB） | **+413,816 B（404.12 KiB）** |
| 再切页 40 轮，停止枚举 | **−160 B** | −128 B | 0 B |
| 达到 10,000 上限后，再枚举 80 轮 | **−264 B** | +16 B | −152 B |

NX5 的 40 轮枚举增加 **2,080 个句柄、280 个已析构组件分配块**；这些块 strong count 为 0，剩余 weak count 全部等于 MCP 持有的引用数。MCP 容器及其独占保留的死组件分配解释了本组在用增长的 **97.64%**；剩余 **10,024 B** 没有在本轮逐对象归类，不将它们强行归给 MCP，也不据此宣称整个应用无泄漏。下一组停止枚举后在用量不再增加。

数值不完全相等有具体背景：NX5 每次 Rich 查询返回 **115 个元素**、每轮新增 **52 个句柄 / 7 个已析构组件块**；X9 对应为 **138 / 75 / 11**。此外 NX5 是新启动进程，本组句柄槽容量从 256 增到 4,096，句柄/顺序容器增加 **92,160 B**；X9 已有较长查询历史，相应 40 轮没有这次容量扩张。因此不能简单按循环次数要求增长字节一致。

### RSS、分配器空闲块及 MMZ

| Controls 状态 | NX5 RSS（KiB） | arena 在用（B） | MCP 可归属存量（B） |
| --- | ---: | ---: | ---: |
| Rich 预热后 | 17,664 | 1,831,408 | 23,200 |
| 40 轮仅切页后 | 17,664 | 1,832,216 | 23,200 |
| 40 轮加树查询后 | 19,088 | 2,256,056 | 437,016 |
| 停止枚举再切页 40 轮后 | 18,460 | 2,255,896 | 437,016 |
| 达到句柄上限后 | 20,560 | 3,757,792 | 1,938,696 |
| 上限后再枚举 80 轮 | **20,560** | **3,757,528** | **1,938,544** |

停止枚举的 40 轮中，RSS 回落 **628 KiB**，arena 系统字节也减少 **737,280 B**，但在用量仅减少 160 B，MCP 保留量没有变化。这说明分配器归还空闲内存可以造成 RSS 回落，不能把它解释成 MCP 已经清掉死句柄。最终 arena 仍有 **2,595,368 B 空闲块**，其中至少 **1,648 KiB** 是完全位于空闲块内部的驻留整页；它们与 MCP 仍占用的分配块是不同类别。

达到上限及后续 80 轮均为 **10,000 句柄、1,340 个失效组件分配块**；槽 generation 上升证实淘汰/复用。NX5 本组 MCP 相关存量约 **1.849 MiB**，X9 对应约 **1.872 MiB**。这是各自固定负载的实测平台，10,000 限制的是句柄数量，不是跨工作负载通用的字节预算。

独立 1 Hz 采样保存 **543 个运行样本，跨度 541.97 秒**，采样最大 RSS 为 **20,560 KiB**，最低 MemAvailable **33,188 KiB**。运行样本的 MMZ 恒为 **12,760 KiB / 6 块**，没有随查询持续增长。另一个末尾样本与正常退出交叠，MMZ 已降为 4,900 KiB，单独保留，不纳入运行阶段范围。RSS 与 MMZ 是不同记账口径，本报告不将两者直接相加。

### 退出、恢复与证据

切换前暂停音乐演示，核对提交线程已在 futex 等待后，对原 PID 8008 发 SIGTERM；该次信号退出由内核回收四个 MMZ 块并关闭 VO，相关警告单独保留，不冒充正常析构结果，也不混入 showcase 增长结论。测试 showcase 按 600 秒时限正常退出，**退出码 0**，MMZ 回到 **4,900 KiB / 2 块**，随后才启动原音乐 ELF。

原音乐程序及启动脚本、showcase 回退程序摘要保持不变。恢复后音乐进程 **PID 18695 / starttime 19232001** 是唯一显示/输入所有者，线程数 3、TracerPid 0；通过 native MCP 恢复暂停时保存的 **第 6 首 Signal Bloom、2:05 进度、65% 音量，并继续播放**。装饰唱片的旋转相位从新进程重新开始，未声称像素完全相同。恢复快照 RSS 7,960 KiB、MMZ 12,760 KiB；音乐进程已经重新启动，该 RSS 不用于宣称内存优化。

证据入口为本地 `evidence/nx5-growth-comparison/2026-10-16/summary.json`。`analyze.py` 校验阶段增量、MCP 独占弱引用、fixture、上限平台、退出/恢复结果和归档摘要；同时保存查询日志、每秒资源、只读工具源码/ELF、版本/布局证明、原始 arena/status/smaps/MMZ、音乐状态及部署清理回执。**54 项本轮诊断文件**按 NX5 部署流程归档并核验后清理，已有应用目录及活动恢复日志保留。`evidence/` 被 Git 忽略，其他机器需另行取得。此次没有修改实现，没有重新执行物理页、实体触摸、WBC 或扫描输出回归，也没有对 music-player 进行长期增长测试。
