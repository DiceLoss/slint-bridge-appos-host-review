列表从 20.37 FPS 恢复到 **29.00 FPS**，动态 RSS 从约 20.5 MiB 降至 **17.0 MiB**。三组实际显示页共 1843200 像素与软件参考完全一致；同时修复了文字缓存淘汰造成的标题漏刷，用户确认滑动流畅、标题同步正常。

## 原因与逐项对照

先用原生 MCP 运行列表往返拖动：预热约 8 秒、测量约 35 秒，按每 150 次成功完成的显示提交计算 FPS，舍弃第一段跨边界批次。验收阈值为 28 FPS。原版重复得到 20.02 FPS、CPU 97.8%，明确失败。

| 变体 | 完成提交 FPS | CPU（单核 100%） | 结论 |
| --- | ---: | ---: | --- |
| 原图 RGB、原混合 | 20.02 | 97.8% | 复现 |
| 预缩放 RGB、原混合 | 20.08 | 97.9% | 仅改变尺寸无明显收益 |
| 预缩放 RGBA、原混合 | 23.36 | 93.8% | TDE 复制起效，但仍未达标 |
| 原图 RGB、NEON 连续混合 | 27.54 | 98.6% | 混合优化有效，仍低于阈值 |
| 预缩放 RGBA、NEON 连续混合 | 29.00 | 91.6% | 达到驱动完成节拍 |

RGBA 对照得到 1342 次 TDE 复制、1341 次缓存命中、零错误。原始 1638×960 RGB 图同时不满足当前 TDE 的尺寸/格式/不缩放要求；RGBA 对照使背景使用现有复制路径，没有扩展硬件作业范围。

设备没有 `perf`。临时 libc 采样库用 `ITIMER_PROF` 收集 4412 个指令地址，再按同一二进制符号和进程映射归类；约 55.1% 的样本位于软件 renderer 的圆角矩形绘制，6.2% 位于写页格式转换。此采样含启动和短时静止，只用于定位热点，不作为最终帧率成绩。采样库不加载 SDK，复测版本未加载它。

## 实现

- NX5 的 `TargetPixelBuffer` 保留预乘 RGBA 画布，对同色连续像素使用精确的 8 像素 NEON 混合；不透明填充保持批量填充，尾部和无 NEON 构建使用标量算法。RGB 的 `/255` 向下取整、alpha 的原舍入、边界和源颜色保持与 Slint 一致。
- 背景原始 PNG 保留。主机 `build.rs` 将它转换为 1024×600 RGBA PNG 并嵌入应用，设备只解码目标尺寸图片。运行时缩图诊断版曾达到约 37 MiB RSS 峰值，因此正式版采用构建期处理。
- 列表仍为半透明圆角行，照片仍参与背景与混合；没有以不透明列表或纯色底图换取帧率。其他窗口尺寸继续使用 `cover`，不满足 TDE 条件时软件回退。

## 实际页检查发现的标题漏刷

第一轮优化版 `f94c9a0` 的六页 MCP 检查通过，但真实 framebuffer 与完整软件截图的比较发现：列表照片和内容一致，页标题仍显示 Overview；3040 个像素不同。新进程初次切页正常，经过缓存使用和切页后再次复现。原始失败图和页数据保留。

这个问题在原图 RGB、纯软件 renderer 和主机保留缓冲上也复现，与 TDE 或新增混合计算无关。根因是 Slint 文字布局缓存淘汰条目时释放了依赖 tracker，却没有通知依赖该缓存的重绘 tracker，后续文字变化因此可能漏刷；完整截图重新绘制，掩盖了真实页面的旧文字。

Slint `22804ff` 在缓存淘汰后通知依赖，通知发生在释放缓存借用之后，允许 dirty handler 重入；缓存容量限制保持不变。新增单元测试在修复前失败，覆盖淘汰、保留条目和重入。真实展示应用的 [重绘回归](../test-app/tests/showcase_repaint.rs) 直接更新文字模型，并以独立 renderer 对照标题，避免用截图清空被测缓存；禁用通知的负对照失败，恢复修复后通过。

## 最终实机性能与内存

最终构建重新执行四个场景，每场景预热约 8 秒、测量约 60 秒；不截图、不录制 MCP 事件。只读 evdev 观察器确认没有实体输入混入窗口。共 6300 次有效完成提交，统计方式与 [原图片版](nx5-image-background.md) 相同。

| 场景 | 原图片版 FPS | 最终 FPS | RSS（KiB） | CPU 中位数（单核 100%） |
| --- | ---: | ---: | ---: | ---: |
| 动画 | 29.00 | **28.98** | 17304–17368 | 69.1% |
| 列表滑动 | 20.37 | **29.00** | 17436–17436 | 94.6% |
| 图片透明混合 | 29.00 | **28.97** | 17440–17440 | 61.8% |
| 透明开口 | 29.00 | **28.90** | 17444–17444 | 70.0% |

列表比原图片版提高约 **42.4%**，达到当前驱动约 29 FPS 的完成上限；动态 RSS 从约 **20.5 MiB 降至 17.0 MiB**。列表窗口内 RSS 固定为 17436 KiB。CPU 中位数仍约 **94.6%**，余量有限；不能据此认为 CPU 压力已完全消失。相同 MCP 驱动下约 60 秒完成 73 次拖动，原图片版为 53 次；手势定时器也受 UI 负载影响，不是固定频率的外部输入压测。

自动阶段进程 VmHWM 为 17444 KiB（17.0 MiB）；包含后续十张 MCP 截图的同一有限进程峰值为 23408 KiB（22.9 MiB）。最终常驻进程经 UI、截图和用户操作后 RSS 18584 KiB（18.1 MiB）、VmHWM 23372 KiB。这里区分动态窗口与截图临时内存，有限时长的稳定 RSS 不构成长期无泄漏证明。

最终有限进程最后一组统计为 TDE `copy=9882`、`cache_hits=9881`、`errors=0`，背景上传一次后持续命中。`blend=0`：本界面的缩放 alpha 纹理和控件混合由软件/NEON 完成，没有将它们计为硬件混合。
