2026-10-19，延续 [初始 showcase 实测](f1-showcase.md)，对象仍为
`fd_f1_r88r30_spinor-20c31b4578`、D211 RISC-V64、Linux 5.10.44
`#1 Fri May 22 02:04:02 UTC 2026`。本轮重新核对 boot ID、显示所有者、
SD 挂载和恢复程序；boot ID 为 `dac34b8d-d45f-4fb9-a5fc-ba8902eda615`。
ADB 重连已由用户解决，本轮不修改 USB 配置。

## 瓶颈与实验结论

旧版 `f1-g2d` 只接管大块、不透明、无圆角的矩形填充，没有图片回调。
因此 UI 中的壁纸、透明图片、文字、圆角卡片仍由 CPU 绘制。
GE 几乎没有参与主负载：初始富列表窗口 GE IRQ 为 0，Overview 约 1 次/秒。

临时诊断构建在 90 秒 Overview 中记录 1631 次渲染：跳过前 3 帧后，
软件渲染平均 41.29 ms，中位数 35.81 ms；转换/写页分片累计约每帧
11.56 ms。壁纸已经是 1024×600 的等尺寸预乘 RGBA，并非每帧重复缩放。
诊断构建有逐帧日志开销，只用于区分阶段；正式前后对照不保留该日志。
翻页等待与预渲染重叠，不能把这两个 UI 阶段再与 VSYNC 时间直接相加。

离屏微基准使用一个 1024×600 DMA 目标及 512×128 源，20 次重复，
全部成功后读回像素，最后正常释放。以下时间仅对应本探针，不等于 Slint
整帧吞吐；CPU 混合对照是 GCC -O2 的标量循环。

| 有效面积 | GE 复制作业 | CPU 行 memcpy | GE 混合作业 | CPU 标量混合 |
| ---: | ---: | ---: | ---: | ---: |
| 8192 像素 | 0.787 ms | 0.186 ms | 0.807 ms | 1.262 ms |
| 32768 像素 | 0.935 ms | 0.406 ms | 1.028 ms | 4.687 ms |
| 65536 像素 | 1.115 ms | 0.478 ms | 1.329 ms | 8.944 ms |

每次目标 flush/invalidate 各约 9–13 μs，明显小于提交及同步等待成本。
因此全屏背景复制优先 CPU，大块透明混合值得用 GE；小块、零散裁剪不宜逐块提交。

参考 UAPI 注释把 `alpha_en` 的 0/1 含义写反；厂商固定提交的
[normal 驱动](https://github.com/artinchip/luban/blob/13fa021285a307ca345a6b05e0da371b635f18eb/source/linux-5.10/drivers/video/artinchip/ge/ge_normal.c)
实际以非零启用混合。当前镜像的 `IOC_GE_BITBLT` 分支在 `80177e86`，
调用 `801773b2`，其中 `801777f6` 等待 `801769e6` 完成，返回值传回 ioctl；
不是另行调用 GE_SYNC。固定镜像及反汇编获取条件沿用
[内核分析](f1-kernel-analysis.md)。

实测不能机械地将 source/destination 都标记为预乘：该组合与 Slint 比较
出现明显色差：`GE_PD_NONE`、不透明目标时最大偏差为 64，仅取消目标
预乘标志便降至 1。错误搭配 `GE_PD_SRC_OVER` 还会加大偏差。可用组合为预乘 source、非预乘
不透明 destination、`alpha_en=1`、`GE_PD_NONE`；驱动在这个组合中选择
Fs=1、Fd=1-Sa，单次 RGB 舍入差异最多 1。透明目标维持软件，避免引入
不一致的目标 alpha 语义。生产路径成功同步后将已证明不透明的目标 alpha
精确恢复为 255，避免写页时反预乘放大误差。

## 实现与内存限制

修改集中在 `src/backends/f1/g2d*`，无公共 API、feature、Slint 源码或
UI 素材改动。两张物理页、至多一笔翻页和一帧预渲染的机制不变。

1. 等尺寸 RGBA 图片直接按裁剪行绘制，省去通用采样器的坐标/取样开销。
   软件透明合成保持 Slint 整数结果；不透明全屏背景按行复制，只缓存
   不可变源身份和 opacity 判定，不增加全屏像素副本。
2. 大块透明图片允许 GE 混合，使用两个惰性 512 KiB DMA 源槽，
   总量最多 **1 MiB**。源身份和整体 alpha 共同决定复用，源变化重新准备。
   不透明目标检查、几何/面积限制、同步和失败隔离集中在 F1 后端。
3. 缩放、旋转、平铺、染色、字形和透明目标等不适用操作仍走软件。
   GE 自身具有缩放能力，但本轮没有用其过滤方式替换 Slint 的采样规则。
   SVG 若已由 Slint 栅格化为目标大小，可作为等尺寸图片进入 GE。

当前规则、阈值与资源生命周期集中见 [平台说明](software-platform.md)。
两张全屏图片的 DMA 副本会额外消耗约 4.7 MiB，不符合本设备预算；
本轮没有采用该方案，也没有将测试产物放进 RAM 文件系统。

## 实机对照

全部使用 release、同源 Slint、MCP/debug 元数据、同一字体/背景及默认
帧间隔。第一轮每场景预热 3 秒、采样 20 秒；CPU 与 RSS 取 phase 内的
完整资源样本，FPS 取 phase 内首末 trace 的累计提交差和单调时间差。
控制器走设备 loopback，测量窗口内不截图。各有限应用均 `APP_EXIT=0`，
采样控制器均 `PROFILE_DONE` 且退出码 0。

“直接图片”是诊断对照构建；最终版本在其基础上加入受限 GE 混合。

| --- | ---: | ---: | ---: | ---: | ---: |
| Overview | 18.55 | 21.03 | 21.11 | 13.8% | 98.0% → 97.8% |
| Motion | 21.36 | 24.91 | 24.57 | 15.0% | 97.9% → 98.3% |

## 像素、失败与兼容性验证

- 主机直接图片回归覆盖 straight/预乘、整体透明度、嵌套裁剪、全屏
  opacity 判定、共享源变化与不再使用后的释放，要求逐字节一致。
- 缩放/四种旋转的回归确认不适用变换保持软件结果；填充及图片的故障
  注入确认不重试、不访问未知 DMA、不提交错误帧。
- RISC-V ignored `offscreen_texture_cache` 经真实 Slint 回调验证 60 帧，
  18 次硬件混合、12 次上传；其余复用。源变化触发新上传；透明目标回退
  软件且严格相等。所有有效硬件像素最大差异 1，退出码 0。
- 通过原生 MCP 设置相同场景，静止后用只读 framebuffer 工具逐行取回
  1024×600 BGRA 前台页。富列表最大通道差异 1（40126 个通道不同），
  150% 缩放页差异 1（1410 个通道不同）；Layers 40% 和透明窗口场景
  逐字节一致。四组 alpha 均完全一致，没有超过 1 的 RGB 差异。

注入、温度/功耗或长时间稳定性验证，CPU 频率接口仍不可用。

主机 feature 矩阵、fmt、NX5/F1 workspace clippy（含 MCP）通过；
RISC-V F1 clippy 的全部 targets、release 交叉构建、GE ABI 编译检查通过。
主机 F1 定向 8 项回归通过。未改变其他板级后端，未重跑无关 NX5 实机测试。

## 2026-10-19：64 位写页与有界 PNG 硬解

本轮基线为 bridge `248dbb3`，Slint 锁定 `796ea9f`，沿用本节之前的 GE 混合与 1 MiB 源槽。
板为同一 `fd_f1_r88r30_spinor-20c31b4578`，重新核对 boot ID `dac34b8d-d45f-4fb9-a5fc-ba8902eda615`、显示所有者、SD 挂载和恢复程序。
本机报告单核 600 MHz、`rv64gcxthead`、MemTotal 57952 KiB、无 swap；频率是系统报告值，未验证动态频率、温度或功耗。
完整实现保持两张物理页、至多一笔在途提交和一帧预渲染，不改 PAN/VSYNC 完成约定，也没有修改 Slint 源码。

### 指令与写页选择

D211 文档标为 C906FD / RV64IMAFDC，不能按其他 C906V 型号启用 RVV。
实机小进程确认 `revw/srriw` 可执行且交换结果正确；但在本轮普通缓存内存转换中，64 位整数四像素展开更快。
614400 像素的 GCC 标量、玄铁字节操作、四像素 SWAR 中位数分别为 11.966、7.840、5.629 ms。
这是独立转换微基准，不是整帧 FPS；其三个校验缓冲约 7 MiB，没有放入运行库。
资料、工具链和测量边界见[ISA 调查](f1-isa-research.md)。

正式代码使用普通 RV64 指令合并不透明检查与红蓝通道交换，按对齐条件处理前导像素、四像素主体及尾部。
没有新增画布、旋转缓存或解码缓存；遇到透明像素等不适用输入时由原路径覆盖整段。
纯写页候选和最终组合版本分别测量，硬解加载收益不计入持续渲染 FPS。

| --- | ---: | ---: | ---: | ---: |
| Overview | 20.32 | 24.50 | 24.56 | 20.9% |
| Motion | 23.27 | 26.79 | 26.99 | 16.0% |
| 富列表纵向 | 13.29 | 18.27 | 18.35 | 38.0% |
| 富列表横向 | 12.54 | 16.14 | 15.99 | 27.5% |

基线与最终版本共计 7668 次窗口内成功提交。
每场景预热约 5 秒、测量约 25 秒；手势完成会使富列表窗口延长。

### PNG 完整加载与内存

新增公开 `try_decode_png`，直接使用已核验的 VE/DMA UAPI，不加载吞掉 HAL 错误的旧厂商 decoder。
限额与失败规则集中见[平台说明](software-platform.md#f1-png-加载)，原 SDK 问题及成功/失败状态依据见[解码调查](f1-image-decoder-research.md)。
返回图像前，先确认 FINISH、精确输出计数和缓存同步，再复制并按 Slint 规则预乘；临时 DMA 随后释放。
输入直接合并到一个有界 DMA 缓冲，输出只清理硬件要求的上一行，复制后在普通堆内做颜色计算，减少重复清零和 DMA 字节访问。

`image-decode` 对同一编码输入分别预热 3 次、采样 20 次，计时包含解析、准入、分配、硬件等待、CPU 转换与临时资源释放。
分配器计数也在两种模式中启用；它记录 Rust 请求的堆字节，不包含 DMA、内核与所有 libc 内部分配。
为避免进程检查受短命 ADB shell 干扰，正式解码采样期间不持续轮询设备；不截图、不修改输入或缓存策略。

| PNG | 软件中位数 | 硬解中位数 | 默认应用选择 |
| --- | ---: | ---: | --- |
| 1024×600 背景 | 331.60 ms | 145.61 ms | 硬解 |
| 256×160 缩放图 | 10.16 ms | 29.72 ms | 软件 |
| 800×112 蓝色行背景 | 32.69 ms | 35.50 ms | 软件 |
| 800×112 琥珀行背景 | 32.65 ms | 35.56 ms | 软件 |
| 244×328 蓝色卡片 | 27.95 ms | 34.86 ms | 软件 |
| 244×328 琥珀卡片 | 26.88 ms | 34.77 ms | 软件 |

背景完整加载耗时降低 56.1%，约为原来 2.28 倍的加载吞吐；这不是首屏总时间或稳态 FPS 的同比值。
小图的准入与分配等固定开销超过收益，因此 showcase 只对大背景默认硬解，并在显示画布创建前完成。
富列表、缩放 PNG 保持软件加载，SVG 保持 Slint 解析与栅格缓存；JPEG 未接入新入口。
背景 p95 为软件 333.05 ms、硬解 166.10 ms，所有逐次值保留在汇总中。

背景的额外 Rust 堆峰值为软件 7372824 B（约 7.03 MiB）、硬解 2457696 B（约 2.34 MiB），返回图像两者均约 2.34 MiB。
硬解另有 3428352 B（约 3.27 MiB）临时 DMA，包含 IDAT、32 KiB LZ77 和输出。
两者合计的主要瞬时像素/码流分配约 5.61 MiB，比软件堆峰值低约 1.42 MiB；此相加不是完整系统峰值测量，不能把 DMA 忽略后宣称只用了 2.34 MiB。
独立内存诊断中图像与 DMA 同时存在时 MemAvailable 最低 19212 KiB；这是解码探针负载，不是持续 UI 的可用值。

### 正确性、退出与范围

八张 PNG（六个应用素材、两个 RGB/RGBA 夹具）共 1060930 像素，与 Slint 软件解码的预乘字节完全一致。
夹具包含全部五种 filter、首行 Average、257 像素奇数宽、透明边界，以及分割到不同 IDAT 的 zlib 头/尾。

没有在硬件上故意提交坏流或注入超时；未知 DMA 隔离由代码及主机边界检查支持，不宣称已验证真实异常恢复。

`943a05174cb16d4a292516f7f47faaa43b781000ac1d56a92573542b8c24f1c2`。
这不替代动态扫描、旧页退休或实体触摸验证；本轮不改变原有 PAN/VSYNC 约定。

七种 feature 的主机矩阵、fmt、NX5/MCP 与 F1 RISC-V 全 targets clippy、公开 API 文档、GE/VE ABI 检查通过。

## 2026-10-20：SVG 缩放错位诊断（未修复）

本轮按用户要求保留当前程序并截图分析，不修改运行代码或重新部署。
设备仍为上述 F1、同一 boot ID，实时核对的显示所有者为最终组合程序，starttime 为 `4557231`。
现场是 Image scaling 页，zoom=`148.02744`，SVG 出现阶梯状水平错位，PNG 正常。
两次独立读回当前物理前台页得到相同 PNG SHA256：
`9699c4905361ddd93f1e36a1d381db749f88c91fcd763da965f05f60b83b6792`。

现场 MemAvailable 约 10.6 MiB，低于 MCP 全屏截图所需的 16 MiB 下限，因此只用原生 MCP 查询/改变缩放，
使用既有 `read-front.c` 以 4 KiB 分块读取静止前台页，PNG 在主机转换。
读回前后 yoffset 一致，线程处于 ppoll/futex/epoll 等待；没有重绘截图、写 framebuffer 或操作 SDK。
此读回证明物理页中的错位，不证明扫描输出或旧页退休。

### 原因与对照

问题位于 [F1 GE 原生图片上传](../src/backends/f1/g2d/native.rs)：上传时按 `y * data.width` 紧密排列每行，
提交时第 267 行直接设置 `stride = data.width * 4`，没有满足 GE 的 8 字节行对齐要求。
D21x 用户手册 v2.0.4 印刷/PDF 第 372 页，§10.2.5.7 `SRC_SURFACE_STRIDE`，明确要求 Plane0/1 行跨度 8 bytes 对齐。
手册来源与固定摘要见 [ISA 调查](f1-isa-research.md)；本地 PDF 为 `evidence/f1-display-20261019/source/D21x_User_Manual.pdf`，需另行取得。

同源 Slint 的单 Image、纯软件诊断实际记录如下。F1 对照通过原生 MCP 设置比例，并读回物理页：

| 缩放 | SVG 栅格尺寸 | 当前 GE 源 stride | 8 字节对齐 | F1 画面 |
| --- | --- | ---: | --- | --- |
| 100% | 256×160 | 1024 B | 是 | 正常 |
| 148% / 148.02744% | 379×237 | 1516 B | 否 | 阶梯状错位 |
| 150% | 384×240 | 1536 B | 是 | 正常 |

`check-vertical-border.py` 按 SVG 已知的 x=16 竖直边框和 MCP 实际控件位置检查 92 行：
100%/150% 时 PNG/SVG 均为 92/92；148% 和原现场 PNG 为 92/92、SVG 为 9/92，返回失败。
主机诊断使用相同 SVG、Slint 锁定版本和 `DrawTextureArgs`，在 100→148.02744→150→148.02744% 的纯软件绘制中边框均为 46/46。
其 148.02744% 源尺寸确为 379×237，byte_stride=1516，字节数 359292；不是 SVG 文件或布局尺寸本身错误。
变化尺寸后再次返回原比例，物理截图与原现场逐字节相同；错误不依赖沿用前一尺寸缓存。

SVG 先按目标尺寸栅格化，源尺寸等于目标尺寸，因而进入 [GE 的 1:1 图片路径](../src/backends/f1/g2d.rs)。
PNG 在缩放时仍为 256×160 源图，此场景走软件缩放，没有经过该 GE 上传路径。
同样缺陷也可能影响符合 GE 准入条件的奇数宽 RGBA 图片，不限于 SVG。
这是源行布局不满足硬件约束；未读取 GE 内部地址生成状态，不将具体的低位截断算法当作已验证事实。

### 遗漏条件与修复边界

该上传布局来自 `0e6cea5`；上轮 `aec32c5` 的 64 位写页与 PNG VE 解码没有修改这段 GE 实现。
原 [缩放回归](../test-app/tests/showcase_scaling.rs) 仅使用 50/100/125/200%，均产生偶数宽，而且使用纯软件 renderer。
原 [实机 GE 图片回归](../src/backends/f1/g2d/native/hardware.rs) 使用 300×160，stride=1200 同样满足对齐。
因此既有通过结果不覆盖“奇数栅格宽度 + 实际 GE 图片上传”的组合。

修复应将 GE 源缓冲行跨度补齐到 8 字节，并同时修改上传行偏移、提交 stride 和槽容量检查；逻辑宽度与 crop 保持实际图像宽度。
379×237 情况应使用 1520 B/行，比当前紧密布局多 948 B，须仍遵守每槽 512 KiB、总计 1 MiB 的现有上限。
最小规避方式是在提交前把不满足对齐的图片交给 CPU；本轮未实施任何一种方案，也未宣称硬件修复验证通过。
后续回归需包含奇偶相邻宽度、缩放切换、裁剪和槽容量边界，并通过实机 GE 路径与软件像素对照。
